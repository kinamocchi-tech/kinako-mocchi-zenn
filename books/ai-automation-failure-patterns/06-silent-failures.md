## 毎日「成功」していた収集

SNS の指標は、毎日自動で収集していました。収集のログには毎日、成功の件数が並びます。スナップショットのファイルも毎日 1 つずつ増え、収集状態の欄は毎回「ok」でした。鮮度の監視も、ファイルの日付が新しいので合格を返していました。

ある日、ダッシュボードを見た人から「この数字、ずっと同じではないか」と言われました。確かめると、ある 1 つのプラットフォームの累計再生数が、19 日間 1 も変化していませんでした。

収集に誤りはありませんでした。そのプラットフォームへの新規投稿が 19 日前から止まっていて、既存の投稿の数字は伸びきっていたのです。合計が動かないのは、API が返した正しい値でした。止まっていたのは収集の上流、短尺動画の製作です。その製作も、毎回「上限に達したので今回は待機」という正常な判定で終了していました。

誰も嘘をついていません。どの処理も、自分の担当範囲では正しく動いていました。

## 兆候：48 件を 7 つの類型に分ける

この分類は 48 件で、8 分類の中で最も多く、4 か月目以降に 33 件が集中しています。48 件を「何が正常の顔をしていたか」で分けると、次の 7 つになりました。

| 類型 | 件数 | 正常の顔をしていたもの |
|------|----:|---------------------|
| F 終わっていない工程を完了と扱う | 16 | 「完了」の記録。工程の欠落・仮置きのまま公開・修正の未配信 |
| C 例外・経路の穴で検査が効いていない | 7 | 検査の合格。実際には検査が走っていない |
| E 値の停滞・古さを見ていない | 7 | 「新しいファイルがある」。中身は動いていない |
| A 失敗を空・不在・正常値に丸める | 5 | 「対象なし」「存在しない」。実際は照会に失敗していた |
| D 代理指標・環境差で測り違える | 5 | 正常な判定値。測っている量が違う |
| B 0 件・空の結果を合格とみなす | 4 | 「違反 0 件」。実際は 1 件も走査していない |
| G 測れないことを壊れたと報告する（誤報） | 4 | 「停止中」の警告。実際は動いている |

最後の G だけは向きが逆です。黙るのではなく、鳴り続けます。ただ、鳴り続ける警告は誰も見なくなるので、行き着く先は同じです。

48 件は、記録された件数の下限です。記録されないまま消えた失敗は数えられないので、実際の数はこれより多い可能性があります。

48 件のうち少なくとも 9 件は、記録の本文に「運用者が画面を見て指摘した」「数字を見て気づいた」と書かれていました（キーワード検索で拾える範囲の下限です）。監視の仕組みではなく、人の目が最後の検知器になっていました。

## 類型ごとの実例

**F 終わっていない工程を完了と扱う（16 件）。** 週次の複合スロットが、中の主要工程を外したまま短時間で終わり、3 週連続で「完了」と記録されていました。完了の判定が「実行が終わった」「状態ファイルが更新された」だけで、生成されるはずのレポートの有無を見ていなかったためです。リポジトリ側の設定を直して「直った」と判定したのに、公開先の概要欄は古い内容のまま、という事例も同じ類型です。骨格だけ作って後で人が埋める設計の記事が、骨格のまま公開された事例もあります。

**C 例外・経路の穴で検査が効いていない（7 件）。** 図解画像のガードに、ブランドのロゴを描く場合の例外がありました。その例外が「ロゴ」という 1 語で検査全体を飛ばす作りになっていて、プロンプトに `logo` を足すだけで判定がブロックから通過へ反転しました。この穴を通って、文字の崩れた図解が動画本編と記事にまで公開されています。依存パッケージの一括インストールが全滅し、警告 1 行だけ残して検査フックが無言で無効になっていた事例もこの類型です。

**E 値の停滞・古さを見ていない（7 件）。** 冒頭の 19 日間の事例がこれです。鮮度の監視は「ファイルの日付」しか見ておらず、「中身が動いているか」を見る層がどこにもありませんでした。

**A 失敗を空・不在・正常値に丸める（5 件）。** 課題（Issue）の重複を確認する処理が、課題の一覧を 1 ページ目（100 件）だけ取得して照合していました。総数は 3,600 件を超えていたので、数日前に作った課題はもう 1 ページ目にありません。「存在しない」と判定して同じ課題を作り直し、二重・三重の起票が 35 件たまりました。同じ作りの別の処理は、照会そのものが失敗したときに「既存なし」を返していました。どちらも、**照会に失敗した** ことを **対象が存在しない** ことと同じ値で表していました。

**D 代理指標・環境差で測り違える（5 件）。** 短尺動画の週次上限の判定が、リポジトリの履歴から「直近 7 日に追加されたファイル数」を数えていました。クラウドの実行環境は履歴を浅く取得するので、境界のコミットが既存の全ファイルを「新規追加」に見せます。同じリポジトリで、境界を除かずに数えると 64 本、除くと 1 本でした。判定は導入した日から毎回「上限到達・待機」を返し、製作が止まりました。冒頭の 19 日間の停滞の上流は、これです。

**B 0 件・空の結果を合格とみなす（4 件）。** 発音の事前検査のコード片が、台本のトップレベルのキー名を取り違えていました。走査対象が常に空なので、毎回「未登録の用語なし」と表示して合格します。キー名を直すと 223 行を走査し、未登録の用語が 5 件見つかりました。

**G 誤報（4 件）。** 接続経路の可否を測る処理が、ある経路を「停止中」と記録し続けていました。実際には経路は生きていて、測定に使うコマンドがその環境に入っていないだけでした。値が「停止中」のまま変化しないので、状態変化の通知も一度も出ません。

## 3 層の原因

| 層 | 共通していたこと |
|----|----------------|
| 直接 | 処理が、判定できない状態を「正常」「空」「完了」のどれかの値で返した |
| 仕組みの穴 | 判定の結果に「分からない」の値が無い。検査が「何件見たか」を報告しない。監視が、処理の信号（終了・更新時刻）を見て、生成物の中身を見ていない |
| 前提 | 「異常なら、エラーとして表に出る」という前提。第 1 波・第 2 波の失敗は実際にそうだったので、その前提が強化されていた |

3 層目が、この分類が後半に寄る理由だと筆者は考えています。前半の失敗はうるさく、うるさい失敗を潰すための仕組みが増えました。その仕組みは「エラーが出たら止める」形をしています。正常な顔で返る失敗は、その網を素通りします。

## 仕組みへの昇格：「分からない」を表せる形にする

この分類の昇格は、検査を増やすことではなく、**判定の出口の形を変える** ことでした。

| 類型 | 文書 | AI チェック | フック・関数 |
|------|------|-----------|------------|
| F 完了の扱い | 「完了」の定義を、生成物と配信先まで含めて書く | 完了報告と生成物の台帳を突き合わせる | 定期生成物を台帳に登録し、鮮度を毎時点検する |
| C 経路の穴 | 例外の範囲を明文化する | 例外条項を足す変更をレビューで重点的に見る | 例外は最小の判定にだけ効かせる。依存の欠落は検査の失敗として止める |
| E 停滞 | 「取得できた」と「更新された」を区別して書く | — | 指標ごとに「直近 N 回同じ値なら停滞」を判定する |
| A 丸め | 照会の結果を 3 値で扱うと決める | — | 照会関数を 3 値にし、「分からない」なら起票・削除などの副作用を止める |
| D 代理指標 | 代理指標を使う箇所を列挙する | 環境差（浅い履歴・新規作成の環境・時刻のリセット）を確認する | 「上限到達」系の判定に矛盾ガードを付ける（上限まで作ったはずなのに公開も予約も 0 なら、測り違いを疑う） |
| B 0 件 | 「0 件は合格ではない」と書く | — | 走査件数 0 を異常終了にする |
| G 誤報 | 「測れない」と「止まっている」を別の値にする | — | 測定手段が無いときは「分からない」を返す |

表の右端で共通しているのは、**「分からない」という値を、合格とも不合格とも別に持つ** ことです。A・B・G は、その値が無かったために、分からないことを空・合格・停止のどれかに押し込んでいました。

## テンプレート 1：サイレント失敗 7 類型の点検表

自分の検査・監視・定期処理を 1 つずつ取り上げ、各行に答えます。答えられない行が、その処理の黙る場所です。

| 類型 | 点検の問い |
|------|-----------|
| F | この処理の「完了」は何で判定しているか。生成物の有無と、配信先への反映まで見ているか |
| C | 検査を飛ばす例外・条件分岐はあるか。その例外は、検査のどこまでを飛ばすか。依存が欠けたとき、検査は失敗するか、無言で抜けるか |
| E | 値が動かなくなったら、どこで分かるか。「最後に値が変わった日」を記録しているか |
| A | 照会が失敗したとき、何を返すか。「無い」と「見きれていない」を区別しているか。一覧はすべてのページを見ているか |
| D | 判定に使っている量は、本当に知りたい量か。浅い履歴・新規作成の環境・時刻のリセットで、その量は変わらないか |
| B | 走査した件数を出力しているか。0 件のとき、合格を返していないか |
| G | 測定の手段が無いとき、何を返すか。その値は、状態変化の通知を止めてしまわないか |

## テンプレート 2：3 値で答える照会と、0 件走査のガード

A と B の類型に対応する雛形です。`find` は、すべてのページを見て無かったときだけ「無い」を返し、失敗や打ち切りは「分からない」を返します。呼び出し側は、「分からない」のとき起票などの副作用を止めてください。

```python
"""照会結果を「ある / ない / 分からない」の 3 値で返す（サイレント失敗対策）。"""
from enum import Enum

class Lookup(Enum):
    FOUND = "FOUND"
    NOT_FOUND = "NOT_FOUND"
    UNKNOWN = "UNKNOWN"        # 照会に失敗した・最後まで見きれなかった

def find(fetch_page, match, max_pages: int = 100) -> Lookup:
    """fetch_page(n) は n ページ目の要素リストを返し、空リストで終端を示す。"""
    try:
        for n in range(1, max_pages + 1):
            items = fetch_page(n)
            if any(match(x) for x in items):
                return Lookup.FOUND
            if not items:
                return Lookup.NOT_FOUND    # 終端まで見て、無かった
        return Lookup.UNKNOWN              # 上限で打ち切った＝見きれていない
    except Exception:
        return Lookup.UNKNOWN              # 照会の失敗を「無い」に丸めない

def require_scanned(count: int, what: str) -> int:
    """検査対象が 0 件なら合格ではなく異常として止める。"""
    if count == 0:
        raise SystemExit(f"[gate] {what} を 1 件も走査していません（キー名の誤り・入力の欠落を疑う）")
    return count
```

3 ページ目に対象がある一覧、どこにも無い一覧、2 ページで打ち切った照会、常に失敗する照会の 4 通りと、正しいキー名・誤ったキー名での走査を実行した結果です。

```text
Lookup.FOUND
Lookup.NOT_FOUND
Lookup.UNKNOWN
Lookup.UNKNOWN
走査: 3
[gate] セリフ を 1 件も走査していません（キー名の誤り・入力の欠落を疑う）
```

`require_scanned` は、例外を投げる代わりに終了コード 1 でプロセスを止めます。検査をフックやスケジュール実行に組み込む場合、呼び出し側がこの終了コードを「失敗」として扱っているかも確かめてください。

## テンプレート 3：生成物の鮮度台帳

E と F の類型に対応します。定期的に作られるべき生成物を台帳に登録し、「最新はいつか」と「値が動いているか」を点検します。結果は OK・STALE（古い）・STUCK（値が動いていない）・UNKNOWN（判定できない）の 4 つで、UNKNOWN を最も重く扱います。

台帳は JSON の配列です。パスと値はプレースホルダーです。

```json
[
  {"name": "SNS 指標スナップショット", "glob": "<スナップショットの置き場所>/*.json",
   "max_age_hours": 48, "time_field": "generated_at",
   "must_change": "total_views", "stuck_after": 3},
  {"name": "週次レポート", "glob": "<レポートの置き場所>/*.md", "max_age_hours": 192}
]
```

点検スクリプトです。`time_field` を指定すると、ファイルの更新時刻ではなく中身の時刻欄で新しさを判定します。実行環境を毎回作り直す運用では、ファイルの更新時刻が取得した時刻にリセットされ、古いファイルも新しく見えるからです（D の類型そのものです）。

```python
"""定期生成物の「新しさ」と「値が動いているか」を台帳で点検する（OK / STALE / STUCK / UNKNOWN）。"""
import glob, json, os, sys, time
from datetime import datetime

def stamp(path: str, time_field: str | None) -> float:
    """生成時刻。新規クローンで更新時刻がリセットされる環境では、中身の時刻欄を使う。"""
    if time_field:
        return datetime.fromisoformat(json.load(open(path, encoding="utf-8"))[time_field]).timestamp()
    return os.path.getmtime(path)

def check(entry: dict, now: float | None = None) -> tuple[str, str]:
    now = now or time.time()
    tf = entry.get("time_field")
    try:
        files = sorted(glob.glob(entry["glob"]), key=lambda f: stamp(f, tf))
    except (OSError, ValueError, KeyError):
        return "UNKNOWN", "生成時刻を読めない"
    if not files:
        return "UNKNOWN", "生成物が 1 つも見つからない（未登録か、置き場所の変更）"
    age_h = (now - stamp(files[-1], tf)) / 3600
    if age_h > entry["max_age_hours"]:
        return "STALE", f"最新が {age_h:.0f} 時間前（上限 {entry['max_age_hours']} 時間）"
    field, n = entry.get("must_change"), entry.get("stuck_after", 0)
    if field and n and len(files) >= n:
        try:
            vals = [json.load(open(f, encoding="utf-8")).get(field) for f in files[-n:]]
        except (OSError, ValueError):
            return "UNKNOWN", "中身を読めない"
        if len(set(map(json.dumps, vals))) == 1:
            return "STUCK", f"{field} が直近 {n} 回すべて {vals[-1]!r} のまま"
    return "OK", f"最新 {age_h:.0f} 時間前"

if __name__ == "__main__":
    ledger = json.load(open(sys.argv[1], encoding="utf-8"))
    worst = 0
    for e in ledger:
        state, why = check(e)
        print(f"{state:8} {e['name']}: {why}")
        worst = max(worst, {"OK": 0, "STUCK": 1, "STALE": 1, "UNKNOWN": 2}[state])
    sys.exit(worst)
```

値が 3 日続けて同じスナップショット、10 日前で止まったレポート、1 つも存在しない生成物の 3 件を台帳に登録して実行した結果です（更新時刻で判定する設定）。

```text
STUCK    SNS 指標スナップショット: total_views が直近 3 回すべて 1470 のまま
STALE    週次レポート: 最新が 240 時間前（上限 192 時間）
UNKNOWN  月次サマリー: 生成物が 1 つも見つからない（未登録か、置き場所の変更）
exit=2
```

中身の時刻欄で判定する設定でも、値が固まった指標を STUCK、値が動いている指標を OK と判定することを確かめています。

STUCK は「壊れている」という意味ではありません。冒頭の事例のように、値そのものは正しいこともあります。STUCK が言っているのは「上流を見に行け」です。`stuck_after` を 3 にしておけば、値が固まってから 3 回目の点検で STUCK が出ます。冒頭の 19 日間の停滞は、この設定なら数日のうちに表へ出る計算です。

## 新しい生成物を作ったら、台帳に足す

台帳は、登録されたものしか見ません。筆者の運用でも、監視は事故が起きるたびに 1 つずつ手で足してきました。新しい定期処理を作るときに台帳への登録を手順に入れておかないと、次に黙る生成物は、台帳の外から現れます。

もう 1 つ、照会関数・ガード・台帳・点検・通知は、どれも処理や監視の **数を増やす** 方向に働きます。増えた仕組みは、それ自体が管理の対象になります。後半の記録には、仕組みが増えたこと自体が事故の原因になった失敗も、少なからず残っていました。
