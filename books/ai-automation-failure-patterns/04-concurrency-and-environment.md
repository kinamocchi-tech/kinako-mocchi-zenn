## 二重投稿は、直すたびに形を変えて戻ってきました

同じ速報が SNS に 2 回投稿されたとき、原因はすぐに分かったつもりでした。投稿済みの記録を照合する処理が、ある形式の記録を読めていなかった。照合を直して閉じました。

間もなく、また二重に投稿されました。今度は、手動で記録した経路のデータが、URL を複数形の配列で持っていて、単数形のフィールドしか読まない照合をすり抜けていました。しかも投稿前の確認手順が、同じ照合ロジックを手順書の中に文章で書き直していて、そちらにも同じ穴がありました。直して閉じました。

その翌日、また起きました。照合のロジックはもう正しかったのに、です。

## 並行実行・状態の衝突：兆候

この回の原因は、照合ではなく **記録の置き場所** にありました。筆者の運用では、毎時の実行がそれぞれ新しい作業環境を作り、共有のリポジトリから最新を取ってきます。1 つめの実行は投稿の記録を書きましたが、その記録はまだ本流に取り込まれていない変更の中にありました。2 つめの実行からは見えません。だから、正しい照合が「未投稿」と答えたのです。

31 件の衝突の兆候は、この事例と同じく **2 つの正しい処理の組み合わせ** で現れます。

- **二重に実行する。** 別の実行が対応中の変更提案（プルリクエスト）に、毎時の巡回が「放置されている」と判断して介入しました。動画のレンダリングまで二重に走り、約 40 分を無駄にしています。巡回は作成からの経過時間だけを見ていて、作成した実行がいま動いているかを見ていませんでした。
- **消す。** セッション開始時の初期化処理が、前回の残骸を掃除するつもりで、未コミットの作業を巻き戻していました。異常終了したセッションの作業がまるごと消えます。バックグラウンドで動画を書き出している最中に、別の処理が共有の一時領域を一括削除して出力を壊した事例もあります。
- **番号が飛ぶ。** 連番の採番を 3 つの並列サブエージェントに分けたところ、それぞれが「現在の最大値 + 1」を計算して衝突し、再採番を繰り返して番号が大きく飛びました。
- **保護された場所へ書く。** 作業ブランチが本流と同じ状態に追いついたのを見て「もう同じだから」と判断し、本流へ直接書き込んでいました。

## 並行実行・状態の衝突：3 層の原因

| 層 | 共通していたこと |
|----|----------------|
| 直接 | 2 つの実行が、同じ対象（投稿・提案・作業ツリー・番号・一時領域）に、互いを知らずに触った |
| 仕組みの穴 | 「いま誰が触っているか」と「どこまで記録が届いているか」を確かめる手段が無い。状態が、実行ごとに別々の場所にある |
| 前提 | 処理を 1 本ずつ設計していた。各処理は単独で正しく、並行に走ることは設計の外だった |

二重投稿の最終的な対策は、記録の照合を精緻にすることではありませんでした。**実際に公開されたタイムラインそのもの** を照合先に加えたことです。記録がどこに置かれていようと、公開された事実は全実行から同じに見えます。

## 実行環境・権限・認証：兆候

この分類は 6 か月目に急増し、その月の記録の 45% を占めました。中身はほぼ「無人の実行が止まる」です。

- **承認待ちで丸一日止まる。** 無人のスケジュール実行が、設定ディレクトリ配下のファイルを編集しようとして承認プロンプトを出しました。応答する人がいないので、そのまま止まります。8 回分のスケジュール実行が丸一日止まり、人が画面を見て気づくまで誰も検知しませんでした。直前に、権限の補償統制を強める変更が入っていて、その変更が無人実行の編集経路を 1 本も残さない形にしていました。
- **ガードが落ちて承認待ちになる。** 実行前に入力を検査するフックが、内部のコマンド失敗でスクリプトごと終了しました。標準エラー出力も空です。エージェント基盤の仕様では、実行前フックが **終了コード 2** で終わればブロック、**それ以外の非ゼロ** はブロックしないエラーとして扱われ、通常の権限確認に進みます。ガードは効かず、代わりに承認プロンプトが出て止まりました。
- **環境が膨らんで全コマンドが止まる。** セッションを再開するたびに環境変数のファイルへ追記する処理があり、10 回ほどの再開で数千行に膨らみました。最後はシェルの起動時に引数長の上限を超え、`echo` すら実行できなくなりました。
- **外からの経路が遮られる。** クラウドの実行環境から、自前で置いた中継プロキシ経由でアップロードしていたところ、中継側の防御機能がクラウドの IP を遮断しました。

## 実行環境・権限・認証：3 層の原因

| 層 | 共通していたこと |
|----|----------------|
| 直接 | 権限・環境・経路が、対話で動かしていたときと無人のときで違った |
| 仕組みの穴 | 無人の環境で一度も実測していない。止まったことを知らせる経路が無い |
| 前提 | 「手元で動いたものは無人でも動く」「統制を強めるほど安全」という前提。統制の変更が無人実行を止めうるかを評価する観点が無かった |

6 か月目の山は、運用を無人に寄せた時期と重なります。対話のときは人がその場で承認して先に進めていた箇所が、無人にした瞬間にすべて停止点になりました。

## 仕組みへの昇格

| 分類 | 文書 | AI チェック | フック・関数 |
|------|------|-----------|------------|
| 衝突 | 共有資源の一覧と、触る前の確認手順を書く | 変更が共有資源に触れるかをレビュー観点に入れる | 送信は冪等キーを通す。巡回は「直近に活動がある対象」を除外する。破壊的な初期化の直前に新規作業だけを退避する |
| 環境 | 無人で使う経路と、使わない経路を書き分ける | 権限・統制の変更をレビューするとき「無人実行を止めないか」を確認する | 実行前フックは判定が落ちたら止める側に倒す。セッション開始時に環境ファイルを毎回作り直す |

衝突の対策は、どれも「並行に走っても結果が変わらない」形にするものです。ロックで順番を守らせる方向は、実行環境が毎回作り直される運用では効きにくいと分かりました。同じファイルシステムを共有していないので、ファイルのロックは別の実行から見えません。

## テンプレート 1：共有資源の棚卸し表

並行に走る処理を足す前に、触る資源を 1 行ずつ書き出します。「別の実行から見えるか」が「いいえ」の行が、衝突の候補です。

| 資源 | 書く処理 | 読む処理 | 状態の置き場所 | 別の実行から見えるか | 重複・衝突時の扱い |
|------|---------|---------|--------------|------------------|-----------------|
| （例）SNS 投稿 | 告知処理、速報処理 | 両方の投稿前確認 | 送信台帳 ＋ 公開済みタイムライン | 台帳は取り込み後のみ。タイムラインは常に見える | 冪等キーで 1 回に絞る |
| （例）変更提案 | 各実行 | 巡回処理 | 共有リポジトリ | 見える | 直近に活動があれば巡回は触らない |
| （例）作業ツリー | 各実行 | 初期化処理 | 実行環境のローカル | 見えない | 初期化の直前に新規作業だけ退避 |
| （例）一時領域 | 書き出し処理 | 掃除処理 | 実行環境のローカル | 同じ環境内では見える | 処理ごとに専用の下位ディレクトリを使う |
| （例）連番 | 採番処理 | 全処理 | 共有リポジトリ | 見える | 採番は 1 か所でまとめて行い、並列側では計算しない |

## テンプレート 2：冪等キー付き送信と占有判定

二重投稿の事例から、照合に使うキーを **1 つの正規形に寄せる** 処理と、**送ったら直ちに記録する** 処理を 1 つにまとめた雛形です。台帳の置き場所は、全実行から見える場所にしてください。それができない環境では、公開済みのタイムラインなど「外から見える事実」との照合を必ず併用します。

```python
"""外部への送信を冪等キーで 1 回に絞る（並行実行・状態の衝突対策）。"""
import json, os, tempfile, time
from urllib.parse import urlsplit

def canonical_key(record: dict) -> str:
    """記録経路ごとに形がばらつくフィールドを 1 つの正規形へ寄せる。
    単数・複数・キー埋め込みのどれで来ても同じキーになることが要点。"""
    urls = []
    for f in ("source_url", "url"):
        if record.get(f):
            urls.append(record[f])
    urls += record.get("sources") or []
    if not urls:
        raise ValueError("照合に使える URL が無い（キーを作れない送信は止める）")
    u = urlsplit(sorted(urls)[0].strip())
    return f"{u.netloc.lower()}{u.path.rstrip('/')}"

def send_once(record: dict, send, ledger_path: str, ttl_hours: float = 168) -> str:
    key = canonical_key(record)
    try:
        ledger = json.load(open(ledger_path, encoding="utf-8"))
    except FileNotFoundError:
        ledger = {}
    sent_at = ledger.get(key)
    if sent_at and time.time() - sent_at < ttl_hours * 3600:
        return "SKIP_DUPLICATE"
    send(record)
    ledger[key] = time.time()                               # 送った事実をすぐ残す
    fd, tmp = tempfile.mkstemp(dir=os.path.dirname(os.path.abspath(ledger_path)))
    with os.fdopen(fd, "w", encoding="utf-8") as f:
        json.dump(ledger, f, ensure_ascii=False)
    os.replace(tmp, ledger_path)                            # 書きかけを残さない
    return "SENT"

def is_occupied(last_activity_epoch: float, window_min: float = 10) -> bool:
    """直近に誰かが触った対象には手を出さない（横取り防止）。"""
    return time.time() - last_activity_epoch < window_min * 60
```

大文字・末尾スラッシュ・単数形のフィールドで来た記録と、小文字・複数形の配列で来た記録を、同じ台帳で続けて送った結果です。

```text
SENT SKIP_DUPLICATE 送信回数: 1
占有中: True / 放置: False
```

2 件目は別の形で届いても重複と判定され、送信は 1 回だけでした。占有判定は、2 分前に活動があった対象を「占有中」、1 時間前の対象を「放置」と判定しています。10 分という窓は筆者の運用での値で、巡回の間隔と 1 回の処理時間に合わせて決めてください。

## テンプレート 3：無人停止チェックリスト

対話で動いていた処理を無人のスケジュール実行に載せる前に確認します。

- [ ] 無人の環境で、実際に一度通しで実行したか（対話環境での成功は根拠にしない）
- [ ] 承認プロンプトを出しうる操作（設定ディレクトリの編集、作業領域の外への書き込み、未登録のツール、ワークフローの起動など）を洗い出し、許可するか経路を変えるかを決めたか
- [ ] 権限・統制を変更したとき、無人実行の経路が 1 本でも残っているか確認したか
- [ ] 実行前フックが、判定の途中で落ちたときにどう終わるか確かめたか（止める側か、素通りか）
- [ ] 承認待ち・無応答で止まったことを、外部へ知らせる経路があるか（止まった処理自身は知らせられない）
- [ ] セッション開始時に追記するファイルが、再開のたびに膨らまないか
- [ ] 実行環境が毎回作り直される場合、残したい状態（台帳・送信済み記録）を共有の場所に置いているか
- [ ] 外部への経路（プロキシ・中継）が、クラウドの IP から遮断されていないか実測したか

## テンプレート 4：判定が落ちたら止める実行前フック

ガードが落ちて承認待ちになった事例から作った雛形です。判定の処理がどこで異常終了しても、終了コード 2（ブロック）で終わるようにしています。例として、共有の一時領域を一括で削除するコマンドを止める判定を入れました。

```bash
#!/usr/bin/env bash
# 実行前フックの雛形: 判定が途中で落ちたら「止める」側に倒す。
# 終了コード 2 以外の非ゼロは「ブロックしないエラー」として扱われ、ガードが無いのと同じになるため。
set -euo pipefail
trap 'echo "[guard] 判定処理が ${LINENO} 行目で異常終了。安全側で止めます" >&2; exit 2' ERR

input="$(cat)"
cmd="$(printf '%s' "$input" | jq -er '.tool_input.command // ""')"

judge() {
  # ここに自分の判定を書く。例: 共有の一時領域をまとめて消す操作を止める
  if printf '%s' "$cmd" | grep -Eq 'rm[[:space:]]+-[a-zA-Z]*r[a-zA-Z]*f?[[:space:]]+/tmp/?(\*|[[:space:]]|$)'; then
    echo "[guard] 共有の一時領域の一括削除は、他の処理の出力を壊すため止めています" >&2
    return 2
  fi
  return 0
}

rc=0; judge || rc=$?
exit "$rc"
```

設置と登録の最小例です（2026 年 10 月時点の Claude Code の hooks 仕様に基づく一般的な形で、パスは自分の環境に合わせてください）。スクリプトをプロジェクトの `.claude/hooks/guard.sh` に置き、実行権限を付けます。

```bash
chmod +x .claude/hooks/guard.sh
```

`.claude/settings.json` には、ツール実行前（`PreToolUse`）に呼ばれるよう登録します。`matcher` は対象のツール名で、ここではシェルコマンドを実行する `Bash` に限っています。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": ".claude/hooks/guard.sh" }
        ]
      }
    ]
  }
}
```

4 通りの入力を標準入力から与えて、終了コードを確かめました（実行前フックの入力は、ツール名とツールへの入力を持つ JSON です）。

```text
[ls -la] exit=0
[guard] 共有の一時領域の一括削除は、他の処理の出力を壊すため止めています
[rm -rf /tmp/*] exit=2
[rm -rf /tmp/myjob/out] exit=0
jq: parse error: Invalid numeric literal at line 1, column 4
[guard] 判定処理が 8 行目で異常終了。安全側で止めます
[壊れた入力] exit=2
```

4 つめは、JSON として壊れた入力を与えて判定処理を意図的に落としたものです。`trap` の行を消した版で同じ入力を与えると、終了コード 5（jq のエラー）で終わりました。2 以外の非ゼロなので、ガードは素通りになります。

注意点が 2 つあります。止める側に倒すと、判定のバグがそのまま正当な操作の停止になります。無人の実行では、それが「承認待ち」ではなく「ブロックされて別の手を探す」になるだけましですが、誤ブロックが続くなら判定を直す必要があります。もう 1 つ、終了コードの扱いは 2026 年 10 月時点の Claude Code の仕様に基づいています。基盤のバージョンを上げたら、最初に確かめ直す箇所です。

## 正しく動いていると、エージェントが言った

衝突と環境の失敗は、ログを見れば何が起きたかが分かります。二重投稿は 2 件の投稿として残り、停止は止まった実行として残ります。

厄介なのは、ログに残るのがエージェント自身の報告だけの場合です。運用 1 か月目から、筆者の記録には「エージェントが完了と言ったが、実際には終わっていなかった」という種類の失敗が、途切れずに続いていました。
