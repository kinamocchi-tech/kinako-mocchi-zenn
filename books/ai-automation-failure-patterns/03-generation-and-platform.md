## 「たまに化ける」は、たまにではありませんでした

読み上げ音声の誤読は、見つけたら辞書に足す。運用の最初から、そういう手順でした。新しい英単語や製品名が台本に出るたびに辞書を育て、聞いて気になった箇所を直す。それで足りていると考えていました。

運用 7 か月目、「文脈に合わない発話が散見される」と指摘を受けて、全台本の読みを機械的に突き合わせました。合成エンジンに文章を渡すと、実際に読み上げる読み（モーラの並び）が返ってきます。それを文脈上の正しい読みと照合したところ、237 本の台本のうち 131 本、約 500 箇所で誤読が見つかりました。「他の」が「たの」、「並べて」が「なべて」、「未達」が「ひつじたち」。自前の置換ルールが別の語に誤爆している箇所もありました。

「たまに」ではなく、半数を超える台本に入っていたことになります。聞いて探すやり方では見つからない量でした。

## 生成物の品質ブレ：兆候

28 件の生成物の失敗は、音声・画像・文章（口調）のどれでも同じ形をしていました。**出力は毎回少しずつ違い、多くは正しく、一部が崩れる。崩れたものは、見ようとしないと見えない。**

- **画像内の文字化け。** サムネイルの日本語が意味不明な文字列に化けたまま、公開予約まで進んでいました。同じプロンプトでも当たり外れがある、確率的な事象です。
- **画像内の捏造。** 図解を生成させると、プロンプトに無い出典名・調査のサンプル数・数値をモデルが補って描き込みました。「それらしい図解」に典型的な部品を、学習データから自己補完した結果です。累計の数値が「月あたり」と単位まで変わっていました。
- **口調の混入。** 登場人物に、別の人物の語尾や、使わない敬語が混ざる。
- **原理的に通らない入力。** 実在企業名を含む図解 7 枚が、安全フィルタで生成できませんでした。プロンプトの言い換えを 5 サイクル繰り返し、約 30 枚分の生成費用と数時間を使ってから、別の表現手段に回して決着しています。後から調べると、弾かれていたのは入力の文面ではなく生成後の画像でした。どう言い換えても通らない種類の失敗です。

## 生成物の品質ブレ：3 層の原因

| 層 | 共通していたこと |
|----|----------------|
| 直接 | 出力が確率的に崩れた。または、モデルが典型的な部品を補った |
| 仕組みの穴 | 生成した後の出力を、照合先と突き合わせる工程が無い。照合先そのもの（意図した文字列・正しい読み）がどこにも記録されていない |
| 前提 | 「指示を正しく書けば、出力も正しい」という前提。指示（入力）は丁寧に検査していたが、出力は検査していなかった |

最後の 5 サイクルの事例も、同じ前提の上にあります。失敗応答を先頭 300 文字で切って記録していたため、「どの段階で弾かれたか」という情報が毎回切り落とされていました。判定材料を捨てたまま、入力を直せば通るはずだと信じて試行を重ねていたわけです。

## 外部プラットフォーム仕様の思い込み：兆候

外部サービスの失敗 23 件は、生成物とは逆の形をしています。出力は毎回同じで、**自分の理解のほうが違っていた** というものです。

- **無関係の 1 件が全体を止める。** 本の原稿を連携リポジトリに同期したのに、本が公開されませんでした。原因は別の記事のタイトルが文字数上限を超えていたことです。デプロイがリポジトリ全体で 1 回の単位になっていて、1 ファイルの違反で全体が中断していました。しかも失敗は管理画面にしか出ず、違反した記事は 2 週間そのまま残っていました。
- **エラー文が原因を指していない。** SNS への投稿が「この操作は許可されていません」という 403 で失敗しました。権限かプランの問題だと読み、確認に時間を使いました。認証・権限・残高はすべて正常で、実際は宣伝的な投稿パターンへのスパム判定でした。同じ本文と URL で、ハッシュタグ 3 個なら成功し、4〜6 個なら 403 になりました（判定は確率的で、時間帯でも揺れます）。
- **応答の形を想像で書いた。** 外部 API の統合コードを、想定したレスポンスの形で書いて完成扱いにしていました。実際の応答とはフィールド名が 4 か所違い、完了判定のフィールドが常に空なので、一度も成功せずに毎回タイムアウトしていました。エージェント基盤のフック入力でも同じことが起きています。公式の形式に無いフィールド名を記憶で書き、読み出しが既定値（空）を返すので、エラーにならずに誤った観測を流し続けました。
- **共有の枠を奪い合う。** 長尺動画と短尺動画が同じ予約公開時刻を使っていたため、空き枠の計算で長尺が押し出され、週 5 本の設定が 3 週間、実質週 3 本になっていました。

## 外部プラットフォーム仕様の思い込み：3 層の原因

| 層 | 共通していたこと |
|----|----------------|
| 直接 | 外部サービスの実際の挙動（デプロイ単位、スパム判定、応答の形、枠の扱い）が想定と違った |
| 仕組みの穴 | 実物で一度確かめる工程が無い。失敗の通知が外部の管理画面にしか出ない |
| 前提 | 「ドキュメントやエラー文の字面が、挙動を正しく表している」という前提 |

生成物とは、確かめる対象が違うだけです。生成物は出力を、外部サービスは自分の理解を、実物と照合していませんでした。

## 仕組みへの昇格

この 2 つの分類は、データ形式ほど機械的には止まりません。筆者の運用で効いた昇格の形は次のとおりです。

| 分類 | 文書 | AI チェック | フック・関数 |
|------|------|-----------|------------|
| 生成物 | 画像の文字は引用符で渡し「一字一句そのまま描く」と指示する。図解には「出典やサンプル数を描き足さない」と書く | 生成後、画像を見て照合先と比べるレビュー | 生成前に指示文の欠落を検査して止める。読み上げは、返ってきた読みを全件照合する監査を必須工程にする |
| 外部仕様 | 切り分け手順（下のシート）を書いておく | エラー応答の全文を読ませて仮説を立てさせる | 外部の制約（文字数・上限）を生成側で先に満たす。外部の失敗を自前の検査で予測する |

生成物の昇格で効いたのは「指示を強くする」と「出力を照合する」の二段構えです。指示を強くしても確率は 0 になりません。照合だけにすると、崩れの量が多いときに作り直しの費用がかさみます。両方を置いて初めて、崩れが公開まで届かなくなりました。

## テンプレート 1：生成後検証チェックリスト

- [ ] 生成物ごとに「照合先」（意図した文字列・正しい読み・使ってよい数値の一覧）を、生成前にファイルへ書き出しているか
- [ ] 画像に焼き込む文字列を引用符つきで渡し、そのまま描くよう明示しているか
- [ ] 図解・資料系の画像で、指示に無い出典・数値・注記を描き足さないよう明示しているか
- [ ] 生成後に、出力を照合先と突き合わせる工程があるか（目視なら照合先を見ながら、機械なら全件）
- [ ] 音声なら、エンジンが返した読みを検査しているか（聞いて探すのではなく）
- [ ] 自前の置換・辞書が、別の語に誤爆していないか検査しているか
- [ ] 崩れたときの作り直しに回数上限があるか
- [ ] 「何度やっても通らない入力」の扱い（代替表現・手作業）が決めてあるか
- [ ] 失敗応答を切り詰めずに全文残しているか

## テンプレート 2：外部仕様の切り分けシート

外部サービスで想定外の失敗が出たら、エラー文の字面で原因を決める前に、上から順に潰します。各行の「確認」が通れば次の行へ進みます。

| 順 | 疑う対象 | 最小の確認 | 通らなかったら |
|----|---------|-----------|--------------|
| 1 | 認証 | 読み取り専用の API を 1 回呼ぶ | 資格情報・有効期限・スコープ |
| 2 | 権限・プラン | 無害で最小の書き込みを 1 回行い、すぐ取り消す | 権限設定・プラン・残高 |
| 3 | 内容 | 実際の内容から要素を 1 つずつ外して送る | スパム判定・文字数・禁止語・添付 |
| 4 | 応答の形 | 実際の応答を 1 件ファイルに保存し、コードの読み出し箇所と突き合わせる | フィールド名・入れ子・単数/複数 |
| 5 | 処理の単位 | 失敗した 1 件を除いて、同じ操作をやり直す | 一括単位の失敗（1 件の違反で全体が止まる） |
| 6 | 共有資源 | 同じ枠・同じ名前を使う別の処理を列挙する | 枠の奪い合い・名前の衝突 |
| 7 | 時間 | 時間を置いて同じ操作を 1 回だけ再試行する | レート制限・一時的な遮断 |

3 行目の「1 つずつ外す」が、403 の事例で原因に届いた手順です。権限を疑う 1・2 行目が正常だったので、内容を疑う段に進めました。

## テンプレート 3：失敗の種類で次の手を決める関数

5 サイクルの事例を受けて作った判定の雛形です。失敗を「何度やっても同じ結果になるもの」「時間を置けば通りうるもの」「それ以外」に分け、試行を続けてよいかを決めます。

```python
"""失敗の種類で再試行の可否と上限を決める（生成物の品質ブレ・外部仕様の思い込み対策）。"""
import json

# 何度やっても結果が変わらない失敗。言い換え・再送を試さず、代替経路へ回す
DETERMINISTIC = {"content_policy", "moderation_block", "invalid_request", "unsupported_parameter"}
# 時間を置けば通りうる失敗
TRANSIENT = {"rate_limit", "timeout", "server_error", "overloaded"}

def decide(error: dict, attempt: int, max_attempts: int = 3) -> str:
    """error は API の失敗応答を切り詰めずに丸ごと渡す。戻り値は RETRY / FALLBACK / STOP。"""
    code = str(error.get("code") or error.get("type") or "unknown")
    if code in DETERMINISTIC:
        return "FALLBACK"          # 原理的に通らない。試行を重ねるほど費用だけが増える
    if code in TRANSIENT and attempt < max_attempts:
        return "RETRY"
    return "STOP"                  # 未知の失敗・上限到達。人か上位の判断へ渡す

def log_failure(error: dict, path: str) -> None:
    """判定材料が切れないよう、失敗応答は全文を残す（先頭 N 文字で切らない）。"""
    with open(path, "a", encoding="utf-8") as f:
        f.write(json.dumps(error, ensure_ascii=False) + "\n")
```

4 通りの入力で実行した結果です。

```text
{'code': 'moderation_block'} 1 -> FALLBACK
{'code': 'rate_limit'} 1 -> RETRY
{'code': 'rate_limit'} 3 -> STOP
{'type': 'weird_new_error'} 1 -> STOP
```

エラーコードの名前は、使う API の実際の応答に合わせて書き換えてください。テンプレート 2 の 4 行目のとおり、実物の応答を 1 件保存してから集合を埋めるのが確実です。安全フィルタのように「入力段で弾かれたか、出力段で弾かれたか」を応答が教えてくれる API なら、その段階も判定に使えます。出力段で弾かれる入力は、言い換えでは通りません。

## 1 つずつなら正しいのに

形式・生成物・外部仕様の失敗は、どれも 1 つの処理の中で完結していました。形式を検査し、出力を照合し、外部の挙動を実物で確かめる。それぞれの処理を正しくすれば止まります。

運用 4 か月目には、記録の 3 割がその前提の通じない失敗でした。速報の二重投稿は、投稿する処理も記録する処理も、それぞれは正しく動いていました。それでも、対策を重ねるたびに再発しました。
