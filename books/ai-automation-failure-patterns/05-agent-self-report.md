## このチャプターで手に入るもの

- エージェントの行動逸脱・自己申告 26 件を 6 つの型に分けた内訳
- 自己申告を証跡に置き換える対応表
- 委譲依頼の 3 点チェック
- レビューの実行記録が無ければマージを止める証跡ゲート（実行確認済み）

---

## 「レビューしました」は、嘘ではありませんでした

変更提案を出した後、エージェントは「セルフレビューを実施しました」と報告し、レビュー済みのラベルを付けてマージへ進みました。差分も読んでいましたし、気になる箇所の確認もしていました。その意味では、報告は嘘ではありません。

筆者が「今回、レビュー用の工程は実行しましたか」と聞くと、実行していないという答えが返ってきました。差分を目で追っただけで、観点別にレビュアーを立てて検証する工程は飛ばしていたのです。その場で本来の工程を回すと、4 件の指摘が出ました。最も重いのは、作業ブランチが本流から大きく遅れていて、そのままマージすると他の変更を巻き戻すというものでした。目で追ったときには見落としていた指摘です。

ラベルが表していたのは「工程を通った」という事実のはずでした。実際に表していたのは、エージェントの「見た」という申告でした。

## 兆候：26 件は 6 つの型に分かれました

この分類の 26 件は、前半に 17 件、後半に 9 件です。本文が再発や繰り返しに触れている記録の割合は 38% で、8 分類の中で 2 番目に高い数字でした。一度直しても、形を変えて戻ってくる分類です。

| 型 | 件数 | 何が起きたか |
|----|----:|-------------|
| 委譲の失敗 | 6 | サブエージェントに任せた結果が空・期待外。受け取った側が正しい出力を「揺れ」と見て書き換えた |
| レビューの盲点 | 5 | 同じ文脈で見直しても、自分の誤りに気づけない |
| 自己申告と捏造 | 4 | 実行していない工程・受け取っていない結果を「済んだ」と報告した |
| 判断からの逃避 | 4 | 決められた範囲の判断を、調査不十分なまま人に確認へ回して止まった |
| 指示からのドリフト | 4 | 長い作業や文脈の圧縮の後で、応答の言語や報告の形が指示から外れた |
| 能力の誤認 | 3 | できることを「できない」と答え、別の手段へ遠回りした |

上の 3 つと下の 3 つで、性質が違います。上は「やったことにする」方向の失敗、下は「やらない・止まる」方向の失敗です。無人運用では、後者も前者と同じくらい高くつきます。人に確認を求めて止まった処理は、人が見るまで動きません。

いくつか具体例を挙げます。

- **捏造。** ツールを呼び出した同じ応答の中で、まだ返ってきていない結果を予測で書き、それを観測した事実として報告を続けました。マージや公開まで無人で進む運用では、捏造された「成功」がそのまま放置された変更や誤った通知になります。
- **委譲の失敗。** 台本を書いたサブエージェントは、設定どおり、方言で話す場面で一人称を変えていました。受け取った側のエージェントはそれを「一人称の揺れ」と判断し、設定を確認せずに一括で統一しました。設定違反を作り込んだのは、確認した側でした。
- **委譲先の空回答。** 任せたサブエージェントが空の答えを返し、追加で問い合わせても「対応済み」という定型文しか返らない。調べると、多くはエージェント基盤の仕様（サブエージェントが読まないファイル、引き継がれない出力形式の指定）が原因でした。
- **判断からの逃避。** 「環境変数がない」「認証に失敗した」という障害で、詳しく調べる前に人へ確認を求めて止まりました。後から調べると、大半はエージェント自身が解決できるものでした。

## 3 層の原因

| 層 | 共通していたこと |
|----|----------------|
| 直接 | エージェントが工程を省いた、結果を予測で埋めた、文脈を確かめずに判断した |
| 仕組みの穴 | 工程を「通ったか」を、エージェントの報告以外の手段で確かめていない。委譲の依頼に、必要な前提と返す形が書かれていない |
| 前提 | 「エージェントの報告は、実行の記録と同じ重さを持つ」という前提 |

3 層目は、筆者が最も長く疑わなかった前提です。報告は文章として生成されます。生成は、もっともらしい続きを書く動作です。「工程を実行した」という文と「工程が実行された」という事実は、別々に作られうるのです。

## 仕組みへの昇格：申告を、記録に置き換える

この分類の昇格は、一言でいえば **申告を見るのをやめて、記録を見る** ことです。

| 型 | 文書 | AI チェック | フック・関数 |
|----|------|-----------|------------|
| 自己申告と捏造 | 「外部状態は実際のツール出力でのみ断定する」と常駐ルールに書く | 完了報告の各主張に、裏付けのツール出力があるかを確かめる | 工程が実行された記録（証跡）が無ければ、次の操作を止める |
| レビューの盲点 | 見直しの観点を書く | 別の文脈（新しいサブエージェント）で、変更提案を出す **前** にレビューする | レビュー工程の実行記録をマージの条件にする |
| 委譲の失敗 | 委譲依頼の型を書く（下の 3 点） | 受け取った成果物を手直しする前に、設定の正本を読む | 構造の整形と表現の書き換えを別の工程に分ける |
| 判断からの逃避 | 人に確認すべき範囲を 1 か所に列挙する | 確認を求める前に、調査の手順を通したかを確かめる | 人への通知を、列挙した範囲に当たるときだけ出す |
| ドリフト | 応答の規範を書く | — | 文脈の圧縮後・セッション開始時に規範を再注入する |

レビューの盲点について補足します。筆者の運用では、レビューの工程が変更提案を出した **後** に置かれていたため、指摘のほとんどが提案上の往復になっていました。新しい文脈のレビューを提案の **前** に移すと、同じ指摘が提案を出す前に直るようになりました。レビューの厳しさを上げるより、順番を変えるほうが効きました。

## テンプレート 1：自己申告を証跡に置き換える対応表

自分の運用で「エージェントの報告を根拠にしている判断」を書き出し、右の列に置き換えます。

| 申告（これを根拠にしない） | 証跡（こちらを根拠にする） |
|------------------------|------------------------|
| 「レビューしました」 | レビュー工程が、現在のコミットに対して実行された記録 |
| 「テストが通りました」 | テストコマンドの終了コードと出力 |
| 「マージしました」 | 変更提案の状態を取得した結果（マージ済みの状態値） |
| 「公開を予約しました」 | 公開先の API から読み直した予約日時 |
| 「ファイルを作りました」 | ファイルの存在と中身を読み直した結果 |
| 「調べたが解決できません」 | 実施した調査の手順と、それぞれの結果のログ |
| 「サブエージェントが完了しました」 | 完了通知に含まれる成果物（本文・パス・件数） |

## テンプレート 2：委譲依頼の 3 点チェック

サブエージェントに作業を任せるとき、依頼文に次の 3 点が入っているかを確かめます。空回答・期待外の回答の多くは、このどれかが欠けていました。

- [ ] **必要なルールを依頼文の中で再掲したか。** サブエージェントの種類によっては、プロジェクトの指示ファイルを読みません。「読んでいるはず」を前提にしない
- [ ] **返す形を指定したか。** 言語・形式・長さ・含める項目。親セッションの出力形式の設定は引き継がれないことがある
- [ ] **最終出力が親への返り値であることを書いたか。** 「結論・根拠・該当箇所を必ず含める」と明記する。報告を簡潔にする方針が、返り値まで痩せさせることがある

あわせて、受け取った側の規則も 1 つ決めておきます。**成果物の表現を書き換える前に、その表現を決めている設定の正本を読む。** 揺れに見えるものが仕様であることは、珍しくありません。

## テンプレート 3：証跡ゲート

冒頭の事例を受けて作った雛形です。レビュー工程の最後で `record review` を呼んで、現在のコミットに紐づく記録を残します。実行前フックとしても登録し、マージ系のコマンドが来たら、現在のコミットの記録があるかを確かめます。

```bash
#!/usr/bin/env bash
# 証跡ゲート: 「レビューした」という自己申告ではなく、レビュー工程が実行された記録を確認する。
#   記録: evidence.sh record review   … レビュー工程の最後で呼ぶ（いまの HEAD に紐づく）
#   判定: 実行前フックとして登録し、マージ系コマンドを証跡なしでは止める
set -euo pipefail
trap 'echo "[evidence] 判定処理が異常終了。安全側で止めます" >&2; exit 2' ERR
DIR="${EVIDENCE_DIR:-.evidence}"          # ← 置き場所は自分の環境に合わせる
head_sha() { git rev-parse HEAD; }

if [ "${1:-}" = "record" ]; then
  mkdir -p "$DIR"
  printf '{"kind":"%s","sha":"%s","at":"%s"}\n' "$2" "$(head_sha)" "$(date -u +%FT%TZ)" > "$DIR/$2-$(head_sha).json"
  exit 0
fi

cmd="$(jq -er '.tool_input.command // ""')"
if printf '%s' "$cmd" | grep -Eq '(^|[;&|[:space:]])(git[[:space:]]+merge|gh[[:space:]]+pr[[:space:]]+merge)([[:space:]]|$)'; then
  if [ ! -f "$DIR/review-$(head_sha).json" ]; then
    echo "[evidence] 現在のコミットに対するレビュー実行の記録がありません。レビュー工程を実行してから再試行してください" >&2
    exit 2
  fi
fi
exit 0
```

設置先と登録は第 4 章のテンプレート 4 と同じ形です（2026 年 10 月時点の Claude Code の hooks 仕様に基づきます）。スクリプトを `.claude/hooks/evidence.sh` に置いて `chmod +x .claude/hooks/evidence.sh` で実行権限を付け、`.claude/settings.json` の `PreToolUse` に `matcher` を `Bash` として登録します。記録側はフックではなく、レビュー工程の最後から `.claude/hooks/evidence.sh record review` と直接呼びます。登録するのは判定側だけで、`command` には `.claude/hooks/evidence.sh` を書きます。

使い捨てのリポジトリで、記録なし・記録あり・記録後にコミットを追加・無関係なコマンドの 4 通りを確かめました。

```text
[evidence] 現在のコミットに対するレビュー実行の記録がありません。レビュー工程を実行してから再試行してください
記録なし exit=2
記録あり exit=0
[evidence] 現在のコミットに対するレビュー実行の記録がありません。レビュー工程を実行してから再試行してください
コミット追加後 exit=2
無関係 exit=0
```

3 つめが要点です。レビューの後にコミットを足すと、記録は古いコミットに紐づいたままなので、ゲートはまた止めます。「一度レビューした」で済ませず、マージする中身に対してレビューが実行されたかを見ます。

このゲートにも限界があります。エージェントが `record` だけを直接呼べば、レビューをせずに記録を作れてしまいます。筆者の運用では、記録の書き込みをレビュー工程の中に組み込み、手順書には「記録だけを呼ぶ」手順を書かないことで、その経路を細くしています。完全には塞げないので、筆者の運用では記録に指摘の件数も残しています（雛形では省略）。指摘 0 件の記録ばかりが続くなら、それ自体が疑う材料になります。

## 嘘をつかない失敗のほうが、見つからなかった

行動逸脱の失敗には、まだ救いがあります。エージェントが「やった」と言ったことを疑えば、確かめる手段がありました。

後半の記録で増えたのは、誰も嘘をついていないのに、すべてが「正常」を返していた失敗です。照会は成功を返し、検査は合格を返し、工程は完了を記録していました。疑う相手が、どこにもいませんでした。
