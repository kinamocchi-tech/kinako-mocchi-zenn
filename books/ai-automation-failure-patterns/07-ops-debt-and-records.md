## 検知を足して閉じた課題が、3 週間後に戻ってきました

SNS 指標の収集が止まったことがありました。停滞を検知して自動で復旧する点検を足し、課題を閉じました。止まったことにすぐ気づけて、自動で手当てされる。再発防止として十分だと考えていました。

21 日後、同じ症状が出ました。収集した結果を共有の場所へ保存する経路が、1 日 1 回の別の処理に依存していて、その処理が保存対象を選ぶときにスナップショットを取りこぼしていたのです。最初の対応では、その「なぜ止まるのか」に手を付けていませんでした。検知は停止を早く見つけますが、停止しなくなるわけではありません。

この記録の分類は、ルール・通知の運用負債です。仕組みを足したのに、足し方のせいで事故が残る、あるいは増える。25 件のうち 44% が本文で再発や繰り返しに触れていて、8 分類で最も高い割合でした。

## 兆候：25 件の内訳

| 型 | 件数 | 何が起きたか |
|----|----:|-------------|
| 人への通知・報告の過多と形の崩れ | 12 | 同じ内容が毎時届く、テストの作り物が本物の警告として届く、報告が経過の羅列で結論が分からない |
| 文書の重複・食い違い | 8 | 同じ定義が 2 か所にあり二重に実行される、片方だけ直して食い違う、実装後も手順書が「未実装」のまま |
| 判断基準の未定義 | 3 | 想定していない状態（レビュアーの片方だけが応答した等）で、どう判断するかが書かれていない |
| 検知だけで閉じる | 1 | 冒頭の事例 |
| 閉じる経路が無い | 1 | 人の対応待ちの課題が、対応後も自動で閉じられずにたまる |

最も多い通知の型から、2 つ挙げます。

**同じコメントが毎時届く。** コメント監視の通知が、同じ 1 件のコメントについて毎時届き続け、受け手はコメントが増えたと誤解しました。通知の条件が「今回検出した件数が 1 以上」で、前回通知したかどうかを見ていなかったためです。重複判定は外部の課題一覧の検索に頼っていましたが、その検索が実行環境で常に失敗し、毎回「新規」と判定していました。さらに、通知の状態を保存していた場所は、実行環境を作り直すたびに消える場所でした。

**作り物の障害が 1 日 5 通届く。** 監視ツールの自己テストが、本物の通知経路をそのまま呼んでいました。テスト用の架空のデータが、実在しない障害の警告として 1 日 5 通届きました。しかも通知の末尾には「詳細はこのコマンドで」と、通知を出すコマンドそのものが案内されていて、確認するたびに再送される作りでした。

文書の型も 1 つ挙げます。日次の進捗レポートが毎日 2 通届いていました。スケジュール全体の定義ファイルと、ある手順書の中に、同じ時刻の処理がそれぞれ書かれていて、両方が読み込まれて両方が実行されていました。

## 3 層の原因

| 層 | 共通していたこと |
|----|----------------|
| 直接 | 同じ事実・同じ処理を 2 か所以上で持っていた。通知を「出来事」ではなく「件数」で出していた |
| 仕組みの穴 | 足す経路はあるのに、まとめる経路・消す経路・閉じる経路が無い。通知の状態が永続化されていない。テストと本番の経路が分かれていない |
| 前提 | 「仕組みは足すほど安全になる」という前提。事故のたびに 1 つ足すやり方は、前半の失敗にはよく効いたので、疑われなかった |

第 6 章の最後で触れたとおり、後半の対策は仕組みを増やす方向に働きます。その増え方を管理しないと、増えた仕組みが次の事故の材料になります。

## テンプレート 1：失敗記録のフォーマット

本書の集計は、失敗のたびに残してきた Markdown の記録が素材です。後から数え、分類し、昇格を判断できるように、筆者の記録の欄を整理し直したのが次の型です。`<>` の中を埋めて使います。

```markdown
### <記録 ID>: <何が起きたかを 1 文で。症状ではなく仕組みの言葉で>（<記録日>）

- **分類**: <8 分類のどれか。迷ったら「最初に直すべきだった層」で決める>
- **発見経路**: <自動検知 / 人が画面で気づいた / 利用者の指摘 / 別作業中に偶然>
- **発生から発見まで**: <分かる範囲で。不明なら「不明」と書く>

**兆候**: <最初に何が見えたか。エラー文・数字・画面の状態をそのまま>

**3 層の原因**:
- 直接: <その場で何が誤っていたか>
- 仕組みの穴: <なぜそれが止まらずに通ったか>
- 前提: <その穴を作った、疑っていなかった思い込み>

**効かなかった手**: <試して効かなかったこと。無ければ「初回のため無し」>

**対策**: <何を変えたか>

**昇格**: <文書 / AI チェック / フック・関数 のどこまで上げたか> — 理由: <その段で止めた理由>

**再発したら**: <次に同じ形が出たら、どこまで上げるか>

**見直し期限**: <この記録を消すか残すかを判断する日>
```

既存の記録と比べて足した欄は 4 つあります。**分類** は、後で数えるためです。**発見経路** と **発生から発見まで** は、サイレント失敗を測るためです。第 6 章の「少なくとも 9 件」が下限の推定にとどまったのは、この欄が無く、本文の言い回しから拾うしかなかったからです。**見直し期限** は、記録そのものが運用負債にならないための欄です。

## テンプレート 2：分類別の昇格判断表

筆者の 229 件から、分類ごとに「前半に記録された割合」「本文が再発に触れている割合」「対策の本文がフック（実行前後に走る検査）に触れている割合」を数え、それを踏まえて筆者が置いている到達段の目安を右端に書きました。比率は本文の言い回しから機械的に拾った値で、厳密な再発率ではありません。

| 分類 | 件数 | 前半の割合 | 再発への言及 | フックへの言及 | 到達段の目安 |
|------|----:|----:|----:|----:|-------------|
| データ形式・スキーマの崩れ | 21 | 90% | 29% | 33% | 初回から関数・フック。判定が機械的に書ける |
| 生成物の品質ブレ | 28 | 79% | 21% | 29% | 指示の強化（文書）と出力の照合（関数）の二段構え |
| 外部仕様の思い込み | 23 | 65% | 30% | 26% | 切り分け手順（文書）＋ 外部の制約を生成側で先に満たす（関数） |
| 並行実行・状態の衝突 | 31 | 65% | 32% | 35% | 冪等キー・占有判定（関数）。ロックより「並行でも結果が変わらない」形 |
| エージェントの行動逸脱 | 26 | 65% | 38% | 23% | 申告を証跡に置き換える（フック）。委譲の型（文書） |
| ルール・通知の運用負債 | 25 | 60% | 44% | 32% | 定義を 1 か所に寄せる（文書の構造）＋ 状態変化の通知（関数） |
| 実行環境・権限・認証 | 27 | 56% | 33% | 48% | 無人での実測（手順）＋ 落ちたら止める実行前フック |
| サイレント失敗 | 48 | 31% | 19% | 21% | 判定の出口を 3 値にする（関数）＋ 生成物の台帳（定期点検） |

数字から読めることが 2 つあります。

1 つめは、実行環境の分類でフックへの言及が最も多い（48%）ことです。次いで並行実行（35%）、データ形式（33%）、運用負債（32%）が続きます。環境と権限の問題は、文書を読ませても防げません。読む前に止まるからです。

2 つめは、サイレント失敗の再発への言及が最も少ないことです。再発していないのではなく、再発しても気づけないので、記録に「再発」と書かれない、と筆者は読んでいます。この分類だけは、再発の回数を昇格の基準にすると判断が遅れます。1 回目から判定の出口を変えることを勧めます。

## テンプレート 3：状態が変わったときだけ通知する

毎時の再通知の事例から作った雛形です。通知の対象と状態を受け取り、前回から状態が変わったものだけを通知文として返します。

```python
"""通知は「件数がある」ではなく「状態が変わった」ときだけ送る（通知の運用負債対策）。"""
import json, os

def transitions(current: dict, state_path: str) -> list[str]:
    """current は {対象キー: 状態}。前回から変わったものだけを通知文として返す。"""
    try:
        prev = json.load(open(state_path, encoding="utf-8"))
    except FileNotFoundError:
        prev = {}
    msgs = []
    for key, st in current.items():
        if prev.get(key) != st:
            msgs.append(f"{key}: {prev.get(key, '新規')} → {st}")
    for key in prev.keys() - current.keys():
        msgs.append(f"{key}: {prev[key]} → 解消")
    tmp = state_path + ".tmp"
    json.dump(current, open(tmp, "w", encoding="utf-8"), ensure_ascii=False)
    os.replace(tmp, state_path)
    return msgs
```

同じ対象を 4 回続けて渡した結果です。2 回目（毎時の再検知）では何も返りません。

```text
1 ['コメント#1: 新規 → 未対応']
2 []
3 ['コメント#1: 未対応 → 対応済み']
4 ['コメント#1: 対応済み → 解消']
```

使うときの注意が 2 つあります。状態ファイルは、実行環境を作り直しても消えない場所に置いてください。消える場所に置くと、毎回すべてが「新規」になり、元の毎時通知に戻ります。もう 1 つ、テストからこの関数を呼ぶときは、状態ファイルも通知の送り先もテスト専用のものを渡し、本物の経路を呼ばない形にしてください。

## テンプレート 4：自分の記録を数えるスクリプトと、月次の棚卸し

最後に、読者が自分の失敗記録で第 1 章の表を作るためのスクリプトです。Markdown の記録から見出しを拾い、キーワードで 8 分類に一次仕分けして、件数と月別の推移を出します。

```python
"""失敗記録（Markdown）を 8 分類の一次仕分けにかけ、件数と月別推移を出す。
キーワードは出発点。最後は人が 1 件ずつ見直す前提で使う。"""
import re, sys
from collections import Counter, defaultdict
from pathlib import Path

RULES = [  # 上から順に評価し、最初に当たった分類を採る（並び順も判定の一部）
 ("サイレント失敗と監視の誤り", r"素通り|サイレント|気づかれ|見逃|黙って|0 ?件|固着|誤報|鮮度|検知(でき|され)な|完了扱い|放置され"),
 ("エージェントの行動逸脱・自己申告", r"捏造|自己申告|サブエージェント|委譲|確認に逃|英語に切り替|報告して|プラン提示|誤判断|誤答"),
 ("並行実行・状態の衝突", r"並行|競合|重複(投稿|送信|起票)?|二重|レース|未コミット|巻き戻|上書き|wip|ブランチ|main に直接"),
 ("実行環境・権限・認証", r"権限|承認プロンプト|認証|トークン|403|プロキシ|タイムアウト|環境変数|不在|クラウド環境|E2BIG|SSL"),
 ("外部プラットフォーム仕様の思い込み", r"API|仕様|上限|文字数|デプロイ|スパム|OGP|プラットフォーム|Zenn|Qiita|note|X "),
 ("生成物の品質ブレ", r"画像|文字化け|読み|発音|口調|語尾|音声|字幕|BGM|誤読"),
 ("データ形式・スキーマの崩れ", r"YAML|JSON|スキーマ|フィールド|型|形式|locale|TZ|タイムゾーン"),
 ("ルール・通知の運用負債", r"通知|ルール|重複定義|SSOT|手順書|ラベル|Issue|ドキュメント"),
]
HEAD = re.compile(r"^#{2,4} (\S+?)[:：]\s*(.+)$")
DATE = re.compile(r"(\d{4})-(\d{2})")

def entries(paths):
    for p in paths:
        cur = None
        for line in Path(p).read_text(encoding="utf-8").splitlines():
            m = HEAD.match(line)
            if m and m.group(1).startswith("L-"):        # ← 自分の記録の見出し形式に合わせる
                if cur: yield cur
                cur = {"id": m.group(1), "title": m.group(2), "body": ""}
            elif cur is not None:
                cur["body"] += line + "\n"
        if cur: yield cur

def classify(e):
    for name, pat in RULES:
        if re.search(pat, e["title"]):                   # まず題名だけで判定
            return name
    for name, pat in RULES:
        if re.search(pat, e["body"][:400]):              # 題名で決まらなければ冒頭
            return name
    return "未分類"

if __name__ == "__main__":
    seen, by_cat, by_month = set(), Counter(), defaultdict(Counter)
    for e in entries(sys.argv[1:]):
        k = (e["id"], e["title"][:12])
        if k in seen: continue                           # 同じ記録の二重掲載を 1 件に
        seen.add(k)
        c = classify(e); by_cat[c] += 1
        if (d := DATE.search(e["title"])): by_month[c][f"{d.group(1)}-{d.group(2)}"] += 1
        print(f"{e['id']}\t{c}")
    print("\n# 件数", file=sys.stderr)
    for c, n in by_cat.most_common():
        print(f"{n:4}  {c}  {dict(sorted(by_month[c].items()))}", file=sys.stderr)
```

標準出力に記録ごとの仕分け結果を、標準エラー出力に件数と月別の内訳を出します。記録 ID の接頭辞（例では `L-`）と、見出しに日付を含める形は、自分の記録の書式に合わせて書き換えてください。

正直に書いておくと、このキーワード仕分けを筆者の 229 件にかけた結果は、筆者が 1 件ずつ判定した分類と **52% しか一致しませんでした**。19 件はどのキーワードにも当たらず「未分類」になりました。一致率が最も低かったのは運用負債（36%）とサイレント失敗（42%）です。サイレント失敗は、記録の題名でも静かでした。「素通り」「気づかれない」と書かれた記録は拾えますが、「工程が完了扱いになる」のような書き方は、何の失敗なのかを言葉の上で名乗っていません。

だからこのスクリプトは、分類の答えを出す道具ではなく、**仕分けの下書きを作る道具** です。月に 1 回、次の手順で棚卸しします。

1. スクリプトで、その月の記録を一次仕分けする
2. 「未分類」と、仕分けに違和感がある記録を 1 件ずつ読み、テンプレート 1 の「最初に直すべきだった層」で分類を決め直す
3. 分類ごとの件数を第 1 章の表の形に並べ、先月と比べる。サイレント失敗の割合が上がっていたら、第 6 章の点検表を自分の監視に当てる
4. 昇格判断表の「到達段の目安」より低い段で止まっている記録を拾い、昇格するか、しない理由を記録に書く
5. 見直し期限を過ぎた記録を、消す（仕組みに昇格済み）か、期限を延ばすかを決める

5 番目を飛ばすと、記録そのものが運用負債の 25 件と同じ道をたどります。筆者の運用では、全セッションに常駐させる記録に行数と件数の上限を機械で掛け、仕組みに昇格した記録は元の文面を消す運用にしています。常駐する記録は、執筆時点で 10 件です。
